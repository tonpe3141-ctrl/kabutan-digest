# 定時タスク手順書（Claude Routine 専用）

このファイルは、マーケットアプリの **時計・分析・通知** を担う Claude Routine の作業手順書です。
人間はその場にいません。判断に迷っても止まらず、ここに書かれた既定動作に従って最後まで実行してください。

呼び出し元（Routine）のプロンプトが対象を指定します。以下では `{SLOT}` と書きます。

| `{SLOT}` | 発火 (JST) | 役割 |
|---|---|---|
| `preopen` | 07:10 | 寄り前。収集の合図 → 待機 → 分析 → 通知。前日の点検も行う |
| `zenba` | 11:40 | 前場。合図 → 待機 → 分析 → 通知 |
| `taibike` | 16:45 | 大引。合図 → 待機 → 分析 → 台帳の理由づけ → 通知 |
| `weekly` | 金 17:00 | 週報。収集はせず、5営業日分の履歴と台帳から週次の総括を書く |

## なぜこの形か

- GitHub Actions の cron は毎日2〜7時間遅れる（実測）。Routine は時刻どおりに発火するので、
  **Routine が「合図」を push し、その push イベントで Actions を即時に起動する。**
- このセッションのネットワークは GitHub と api.anthropic.com 以外に出られない。
  数値やニュースの収集は Actions（`python -m dashboard.build`）がやる。**ここでは取得しない。**
- Routine の push は、このセッション固有の `claude/routine-*` ブランチに置き換えられることも、main に直接届くこともある。
  ブランチに置き換えられたときは、`docs/data/latest.json` など決められたファイルだけを変えたコミットを
  `.github/workflows/merge-ai-branch.yml` が自動で main にマージする。どちらの経路でも合図で収集が走る。

## 共通ルール

- **材料に無い数値を書かない。** 前日比・順位・件数は必ず `tools/ai_brief.py` の要約（＝latest.json）から取る。
- **トークンを節約する。** latest.json・thermo.json を丸ごと読まない（要約で足りる）。書く量も STEP 4 の上限まで。
  同じファイルを何度も読み直さない。
- 投資助言にしない。「買い」「売り」と断定せず、「〜という見方ができる」「〜に注意」に留める。
- 分からないことは「材料不足」「方向感に乏しい」と書く。物語を作らない。
- **日付は自分で計算しない。** このコンテナは UTC で、JST とは最大9時間ずれる。
  時刻が必要なときは必ず `TZ=Asia/Tokyo date` か、下記の Python を使う。
- 承認を求めない。完了まで自律的に進め、最後に短く報告する。
- **push したら終わり。** このブランチの PR を購読したり、`send_later` で定期チェックを予約したり、
  PR にコメントしたりしない。自動マージは Actions がやる。PR が自動で作られていても放置してよい
  （スロットごとに1本、開いたままにしておく設計）。

## STEP 0: リポジトリを最新にする

このセッションにはリポジトリ（kabutan-digest）がチェックアウト済みのはず。**そのチェックアウトを使う**
（push の認可はこのセッションに紐づいているため、別の場所に clone し直さない）。

```bash
cd "$(git rev-parse --show-toplevel 2>/dev/null || echo "$PWD")"
[ -f dashboard/AI_ANALYSIS_TASK.md ] || { cd ~ && [ -d kabutan-digest/.git ] || git clone https://github.com/tonpe3141-ctrl/kabutan-digest.git; cd ~/kabutan-digest; }
git fetch origin main && git reset --hard origin/main
git config user.name  "claude-routine[bot]"
git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
```

このセッションは定時に何度も起こされる（前回の会話の続きになる）。**毎回この STEP 0 から**やり直し、
前回の記憶にある数値やファイル内容を使い回さない。

`{SLOT}` が `weekly` のときは STEP 1・2 を飛ばして **STEP W** へ。

## STEP 1: 収集の合図を push する

```bash
SIGNAL_AT=$(TZ=Asia/Tokyo date '+%Y-%m-%dT%H:%M:%S+09:00')
mkdir -p docs/data/trigger
echo "$SIGNAL_AT" > "docs/data/trigger/{SLOT}.txt"
git add docs/data/trigger/{SLOT}.txt
git commit -m "収集の合図: {SLOT} ($SIGNAL_AT)"
git push origin HEAD:main
echo "SIGNAL_AT=$SIGNAL_AT"
```

push 先は `claude/*` ブランチに置き換えられることも、main に直接届くこともある（2026-09-28 は main に直接届いた）。
どちらでも正しい。`docs/data/trigger/*.txt` の push で **マーケットダッシュボード更新** の
ワークフローが数秒以内に起動し、main にデータを書き込む。

## STEP 2: main にデータが届くのを待つ

最大 20 分。30 秒ごとに確認する。

```bash
python3 - "$SIGNAL_AT" <<'PYEOF'
import json, subprocess, sys, time
from datetime import datetime

signal_at = datetime.fromisoformat(sys.argv[1])
deadline = time.time() + 20 * 60
while True:
    subprocess.run(["git", "fetch", "-q", "origin", "main"], check=False)
    raw = subprocess.run(["git", "show", "origin/main:docs/data/latest.json"],
                         capture_output=True, text=True).stdout
    try:
        slot = (json.loads(raw).get("slots") or {}).get("{SLOT}")
        upd = datetime.fromisoformat(slot["updated_at"]) if slot else None
    except Exception:
        upd = None
    if upd and upd >= signal_at:
        print(f"OK: 収集完了 updated_at={slot['updated_at']}")
        break
    if time.time() > deadline:
        print("TIMEOUT: 20分待っても届きませんでした")
        break
    time.sleep(30)
PYEOF
```

- `OK:` → STEP 3 へ。
- `TIMEOUT:` → Actions が動かなかった可能性が高い。**それでも止まらない。**
  `origin/main` の `slots.{SLOT}.updated_at` が今日（JST）の、その区分の時間帯
  （寄り前 06:00 以降・前場 11:30 以降・大引 15:30 以降）なら、その既存データで STEP 3 以降を続ける。
  日付だけで判断しない（深夜 00:43 に前の日の引けで作られた大引を今日の大引とみなした実測が 2026-09-30 にある）。
  今日のデータが無ければ STEP 6 の通知だけを
  「{SLOT} の収集が届きませんでした（Actions を確認）」という内容で送って終了する。

## STEP 3: main に追随して、材料の要約を読む

```bash
git pull --rebase origin main
python3 tools/ai_brief.py {SLOT}
```

（合図のコミットが main に取り込まれていれば自動で消え、まだなら main の上に載る。どちらでもよい。）

**`docs/data/latest.json` を直接読まない。** 1区分で15〜20万字あり、ほとんどが使わない本文・URL・桁でトークンを浪費する。
`tools/ai_brief.py` が、見立てに要る数字・表・記事の本文の先頭・決算の材料・買う候補を2〜3万字に詰めて出す。
各記事・見出しには `[K3]` のような **参照番号** が付く（K=株探の記事, H=株探の見出し, P=報道の見出し, A=報道の本文, O=公式発表,
W=トレーダーズ・ウェブの短信, X=マクロの本文, C=海外, M=マクロの話題, E=決算。動いた銘柄の材料の記事の1文は A、見出しは P）。`sources` にはこの番号だけを書けばよく、
URL は `tools/ai_write.py` が戻す。要約に無い細部がどうしても要るときだけ、`python3 -c` でその1項目だけを latest.json から引く。

材料の読み方:
- 情報源の重み: 公式発表（O）と TDnet の開示は事実。通信社・全国紙・公共放送（P・A・C）は2社以上なら事実、1社なら「〇〇（媒体名）によると」。
  株探（K・H）は市場の受け止め・話題株の把握に。Yahoo AIトピックスは AI 生成なので裏付けに使わない。
  見方が割れていれば両論で書く。「取れなかった情報源」は「無かった」ではない
- 短信（W）の表題は事実（指標の結果と予想、要人発言）なのでそのまま引いてよい。マクロの本文（X）にイベントスケジュール（☆が重要）と
  FF金利の織り込み（現在・1週間前・1カ月前）がある
- 温度計・業種の強さ・検証の数字・注文の価格は **付け直さない**（要約の数字をそのまま使う）

## STEP 4: 書く（1つの JSON にまとめ、STEP 5 で差し込む）

`/tmp/ai_out.json` に、その区分で書くキーだけを入れる。`method`・`generated_at` は書かない（ai_write.py が付ける）。

| キー | 寄り前 | 前場 | 大引 |
|---|---|---|---|
| `ai_commentary`（4a） | 必須 | 必須（短く） | 必須 |
| `ai_macro`（4b） | 必須 | **書かない**（アプリは寄り前の見立てを出す） | 必須 |
| `ai_earnings`（4c） | 決算があれば | 書かない | 決算があれば |
| `ai_picks`（4d） | 買う候補があれば | 書かない | 買う候補があれば |
| `ledger_notes`・`themes_add`（4e） | — | `themes_add` だけ | 両方 |
| `ai_news`（4f） | 必須 | 書かない | 必須 |

共通の決まり:
- **要約に無い数値を書かない。** 計算し直さない。記事と要約の数字が食い違えば要約を優先し、記事の数字には出所をつける
- 投資助言にしない。「買い」「売り」「上がる」と断定しない。分からないことは「材料不足」と書く。物語を作らない
- 同じ話を2か所に書かない（相場は 4a、金利・為替・商品は 4b、個々の決算は 4c、買う候補の理由は 4d、個別の企業・業界のニュースは 4f）
- **短く書く。** 画面はスマートフォンで、長い文は読まれない。字数は下の上限を守る

### 4a. 相場の見立て `ai_commentary`

`{"headline": "15〜25字", "sections": [{"title": "具体的な見出し", "body": "本文"}], "sources": ["K1", "P3"]}`

セクションは **3〜4個、1つ150〜300字**（前場は2〜3個・150〜250字）:
1. **総括と理由** … 指数・広がり（乖離・騰落・東証33業種）と、なぜ動いたか（株探の相場記事を土台に報道で裏付け。海外・国内材料・需給のどれが主因か）
2. **物色と需給** … 売買代金の上位と新顔・テーマの資金・業種の上位下位。「どこに資金が集まり、どこから抜けたか」を1つの絵に。
   要約の「混み合い・資金の移り先」があれば、置き去りと買われたをテーマで束ねて書く（例: 電線から半導体製造装置へ）。
   ウォッチの銘柄が「置き去り」に入っていたら、必ず名前と対市場の差を挙げ、その銘柄の開示・ニュースの見出しを確かめて、あれば書き、
   無ければ「個別の材料は見当たらない＝資金の移り先の問題」と書く。**相場全体が上がった日に持ち株だけ下がった理由を、材料が無いのに悪材料とこじつけない**
   要約の「需給」にウォッチの銘柄があれば、上値が重い銘柄（上値の出来高50%以上・1週で買残+30%以上）の名前と数字を1〜2文で
   （例: 「○○は半年の出来高の6割が今より上、平均の値段は今より12%上。戻りで売りが出やすい」）。需給は「上がりにくさ」の説明で、
   「下がる」「売り」と書かない。信用残は週1回の残高（日付を添える）。株数は分割を補正済み（要約の数字をそのまま使う）。要約の一言にない読みを足さない
3. **逆張りの視点**（温度計があれば必須）… 温度と帯、追い風・向かい風の軸、論調と値動きのずれ（出尽くし）。過去の成績（backtest）と
   食い違えばそれも書く。ウォッチの銘柄に「印」（3日で急騰・出来高増）があれば名前・3日の騰落・出来高の倍数と、検証の「弱い割合・強い割合」を並べ、
   「市場と違う動きをしやすい（どちら側にも）。向きは読めない」と書く（**「天井」「売り」「過熱だから下がる」と書かない**。検証では急騰した銘柄は翌日も平均では市場を上回った。
   書いてよい行動は、市場とずれても耐えられる株数か・撤退ラインを決めているかの確認まで）。買う候補の銘柄名と指値はここでは書かない（4d とアプリの売買タブにある）。業種の強さの上位・下位は名前と市場差だけ
4. **次の注目点** … 引け後の開示（個々の決算は 4c に任せ1〜2文）、明日の決算予定、今夜〜明日の重要イベント（☆を時刻つきで）

寄り前は 1・2 を「夜間の米国と金利・為替」「前日の東京と今日の想定」に読み替える。

### 4b. マクロ環境の見立て `ai_macro`（寄り前・大引）

4a と同じ形。`headline` はいまのマクロの主題を言い切る（15〜25字）。**3〜4個、1つ150〜300字**。材料が無いセクションは作らない:
金利と金融政策（2年が主導か10年が主導か＝利上げ観測か財政・インフレ警戒か。FF金利の織り込みは変化で）／為替（金利差と向きが合うか・介入）／
商品と地政学（約3年の最高・最低があれば必ず）／株式への波及と次のイベント（業種の感応度・指標の結果と予想の差・☆の予定）。
話題の媒体数が2つ以上なら事実、1つなら出所を明記。市場の織り込み（事実）と自分の見方を混ぜない。

### 4c. 決算から読む `ai_earnings`（寄り前・大引。決算があれば）

```json
{"headline": "いちばん大事な読み（15〜28字）",
 "winds": [{"title": "業界の風向きの見出し", "body": "150〜300字", "codes": ["6652", "6504"]}],
 "items": [{"code": "6652", "read": "何が分かったか 60〜120字", "wind": "業界への含意 40〜90字",
            "peers": [{"code": "6504", "why": "連想の理由 25〜60字"}], "next": "次に確かめること 30〜80字"}],
 "sources": ["E1", "K4"]}
```
- `winds` は1〜2個。複数の会社の説明に共通する需要・コストの話を、**会社の説明（修正の理由・概況・予想の説明）の文言を根拠に**。
  風向きの数は「読んだ開示の中で」と断る。1社だけなら「1社の説明」。下向きも同じ重さで
- `items` は読みどころのある会社だけ **3〜6社**。類似銘柄は要約の「類似」に出た銘柄からだけ選び、すでに動いているか（20日）・
  いつ決算で確かめられるか・前回の決算と矛盾しないかを添える
- 要約の「印（機械）」（進捗率と過去の平均・据え置いた計画での残りの期間・直近3か月の伸び・利益率）は数字の読みどころ。`read`・`next` で使ってよいが、
  「上方修正しそう」と断定しない（「進捗は平均を上回るが、計画は据え置き」の言い方）
- **引け後（15:30〜）の開示は、その日の値動きで評価しない。** 要約に「開示前の値動き（引け後の開示。反応は翌営業日）」とある会社と、その類似銘柄の
  値動きは、決算を知る前の動き。「反応は市場並み」「売られた」「買われた」と書かない（反応は翌営業日の寄りから。「株価の反応は翌営業日に出る」と書く）。
  類似銘柄の値動きも連想の確認に使わず、20日の騰落・次の決算日だけを添える。反応を書けるのは「決算への反応」の欄にある会社だけ
- 「決算への反応」があれば（大引）、上向きなのに下げた・下向きなのに上げた会社を1〜2文で（理由は記事にあるときだけ。無ければ「反応の理由は材料に無い」）
- 数字は材料にあるものだけ。目標株価・注文は書かない（「連想が向かいやすい」「次の決算で確かめたい」の言い方）

### 4d. 買う候補の理由づけ `ai_picks`（寄り前・大引。要約の「買う候補」に短期・中期の注文があれば）

`{"items": [{"code": "4478", "why": "40〜90字"}], "sources": ["K2"]}`

売買タブの注文カードに1行で出る。**候補を足す・外す・並べ替えることはしない**（入口は機械）。注文1件ごとに:
- **なぜ押したか**: 記事・開示・決算で分かる理由（業種ぐるみの下げ、自社や同業の決算、地合い）。分からなければ「材料の報道なし（地合い・需給の押しとみられる）」
- **決算の材料**（要約の「／決算:」）: 自社が下方修正・減益で押したなら「業績を嫌った押し。戻りは鈍い場合も」、同業・類似の決算が上向きなら
  その会社名と向き、次の決算が保有期間（短期10営業日・中期60営業日）の中にあれば「○/○に決算（またぐ）」を必ず書く
- 要約の「需給」に注文の銘柄があり、上値の出来高が50%以上か買残の注意書きがあれば、「上値にしこり（出来高の○%）」と短く添える（条件・並び順は変えない）
- 「買い」「狙い目」と書かない。価格は書かない（カードに出ている）

### 4e. 台帳とテーマ辞書（大引は両方、前場はテーマだけ）

- `ledger_notes`: 要約の「台帳: 理由づけが要る今日の新規」の各銘柄に `{"notes": "1〜2文", "source": "K2"}`。なぜ数字に引っかかったかに、
  記事で裏付けが取れれば材料を添える。取れなければ「記事での裏付けなし」。追加・削除はしない
- `themes_add`: 要約の「テーマ辞書に無い銘柄」のうち、記事・開示・自分の知識でテーマが分かるものだけ `{"name": "...", "themes": ["既存のテーマ名を優先", ...]}`
  （1〜3テーマ。分からない銘柄は書かない。既存の行は変えない）

### 4f. ニュースから読む `ai_news`（寄り前・大引）

`{"headline": "15〜25字", "topics": [{"title": "具体的な見出し", "body": "120〜220字", "codes": ["593A", "6723"]}], "sources": ["A2", "P5"]}`

ニュースタブの先頭に出る。**個別の企業・業界のニュース**だけを、要約の「動いた銘柄の材料」「報道が多かった銘柄」「テーマの話題」
「同業の急騰・急落」と記事の本文を土台に、**2〜3個**（寄り前は夜間の報道と前営業日の引け後の開示から）:
- **材料で動いた銘柄**: どの材料（開示・報道）で、どれだけ動いたか（市場差）。2媒体以上の報道は事実、1媒体なら出所を書く
- **材料が見当たらない動き**: 「業種ぐるみ」なら仲間と一緒の動き、「材料が見当たらない」なら需給・連想・地合いの可能性とだけ書く（**材料をこじつけない**）
- **連想**: 材料が業界の話なら、どこに連想が向かいうるか。銘柄は要約に挙がった銘柄（類似・同じテーマ・動かなかった仲間）からだけ選び、
  「同業の急騰に動かなかった仲間が追いつくとは検証では言えない」ことを踏まえて「連想が向かいうる」の言い方にとどめる
- 相場全体の話（4a）・マクロ（4b）・決算の読み（4c）は書かない。「買い」「狙い目」と書かない。`codes` は本文で触れた銘柄だけ

## STEP 5: 差し込んで、コミットして push する

```bash
python3 tools/ai_write.py {SLOT} /tmp/ai_out.json     # ❌ が出たら直してもう一度
python tools/stamp_assets.py
```
